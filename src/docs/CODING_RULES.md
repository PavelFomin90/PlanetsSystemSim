# Правила написания кода

## 1. Соглашения об именовании

На основе анализа кодовой базы были выявлены следующие соглашения об именовании:

1. **Интерфейсы** именуются с префиксом 'I':
   - `IDot`, `IDotStartProps`, `ICoords`

2. **Классы** используют PascalCase (CamelCase с заглавной буквы):
   - `Dot`, `System`, `Tracker`, `Drawer`, `TranslateController`

3. **Переменные, константы и параметры** используют camelCase:
   - Переменные: `planets`, `dotProps`, `system`, `drawer`
   - Константы: `canvas`, `ctx`
   - Параметры: `dotParams`, `planet`, `clickCoords`

4. **Экземпляры классов** именуются с использованием camelCase, часто с суффиксом 'Instance':
   - `translateInstance`, `trackerInstance`

5. **Функции** используют camelCase:
   - `createPlanet`, `checkPlanetClick`, `draw`

6. **Свойства объектов** используют camelCase:
   - `coords`, `velocity`, `acceleration`, `mass`

7. **Файлам** присваиваются имена в lowercase с расширением .ts:
   - `dot.ts`, `vector.ts`, `index.ts`

Эти соглашения обеспечивают единообразие и читаемость кода в проекте.

## 2. Форматирование кода

На основе анализа кодовой базы были выявлены следующие правила форматирования:

1. **Отступы** используются с помощью пробелов (не табуляции), размер отступа - 2 пробела.

2. **Максимальная длина строки** не строго ограничена, но предпочтительно переносить длинные строки, особенно в выражениях, как видно в методах `move()` и `computeGravityForce()`.

3. **Пробелы вокруг операторов** используются последовательно:
   - Пробелы вокруг арифметических операторов: `+`, `-`, `*`, `/`
   - Пробелы вокруг логических операторов: `<=`, `>=`, `===`, `!==`

4. **Разделение логических блоков** кода выполняется с помощью пустых строк:
   - Между методами класса
   - Между объявлениями импортов и кодом
   - Между логическими блоками внутри методов

5. **Скобки** размещаются по стилю "one true brace style" (1TBS):
   - Открывающая скобка `{` располагается на той же строке, что и управляющая конструкция
   - Закрывающая скобка `}` располагается на новой строке

6. **Перенос длинных строк** выполняется после открывающей скобки или оператора, с дополнительным отступом для продолжения:
   ```typescript
   this.coords.x =
     coords.x + velocity.length * Math.cos(toRadians(velocity.angle));
   ```

7. **Импорты** группируются и сортируются:
   - Сначала идут именованные импорты из внешних модулей
   - Затем идут именованные импорты из внутренних модулей
   - Между группами импортов может быть пустая строка

8. **Константы** объявляются с использованием `const` и размещаются в начале логического блока.

9. **Объявление переменных** использует `const` по умолчанию, `let` только когда необходимо изменение значения.

10. **Анонимные функции** в коллбэках используют стрелочный синтаксис `=>`.

Эти правила форматирования обеспечивают читаемость и единообразие кода в проекте.

## 3. Структура JSDoc

На основе анализа кодовой базы были выявлены следующие правила для документирования кода с помощью JSDoc:

1. **Формат комментариев** использует блочный стиль с тройной косой чертой `/**` и звездочками в каждой строке:
   ```typescript
   /**
    * Описание функции или класса
    */
   ```

2. **Описание** идет первой строкой после открывающего `/**`, каждая строка начинается с `* `:
   - Краткое описание назначения элемента
   - При необходимости - более подробное описание на следующих строках

3. **Пустые строки** внутри комментария обозначаются как ` * ` (звездочка и пробел):
   ```typescript
   /**
    * Краткое описание.
    * 
    * Подробное описание, которое может занимать
    * несколько абзацев.
    */
   ```

4. **Теги** используются для документирования параметров, возвращаемых значений и других свойств:
   - `@param` - для параметров функций и методов
   - `@returns` - для возвращаемого значения
   - `@interface` - для интерфейсов
   - `@property` - для свойств интерфейсов
   - `@class` - для классов
   - `@implements` - для указания реализуемых интерфейсов

5. **Формат тега @param** включает тип, имя параметра в квадратных скобках (если необязательный) и описание:
   ```typescript
   * @param {IDotStartProps} props - Начальные параметры тела.
   * @param {ICoords} [props.coords={x:0,y:0}] - Начальные координаты.
   ```

6. **Типы параметров** указываются в фигурных скобках `{}`:
   - Простые типы: `{number}`, `{string}`, `{boolean}`
   - Комплексные типы: `{IVector}`, `{IDot[]}`
   - Объединенные типы: `{IDot | null}`

7. **Необязательные параметры** обозначаются квадратными скобками вокруг имени параметра:
   ```typescript
   * @param {IVector} [props.velocity=new Vector(0,0)] - Начальная скорость.
   ```

8. **Значения по умолчанию** для необязательных параметров указываются после имени параметра:
   ```typescript
   * @param {ICoords} [props.coords={x:0,y:0}] - Начальные координаты.
   ```

9. **Описание элементов** интерфейсов включает:
   - Краткое описание назначения интерфейса
   - Тег `@interface` с именем интерфейса
   - Теги `@property` для каждого свойства с типом и описанием

10. **Описание классов** включает:
    - Краткое описание назначения класса
    - Более подробное описание при необходимости
    - Тег `@class` с именем класса
    - Тег `@implements` при реализации интерфейса

11. **Конструкторы** документируются отдельно с описанием всех параметров и их значений по умолчанию.

12. **Методы** документируются с описанием их назначения, параметров и возвращаемого значения.

13. **Правила договорённости по документированию кода**:
    - Все публичные классы, интерфейсы, методы и функции должны быть задокументированы.
    - Внутренние (private) методы — по желанию, но рекомендуется при сложной или неочевидной логике.
    - Описание должно включать:
      - Назначение элемента.
      - Контекст его использования.
      - Особенности поведения (побочные эффекты, асинхронность, мутации, условия).
    - Использовать активный залог: *«Вычисляет вектор силы притяжения»*, а не *«Вектор силы притяжения вычисляется»*.
    - Избегать избыточности: не дублировать имя метода или параметра в описании.
    - Все неочевидные алгоритмы (например, физические формулы, оптимизации) должны быть задокументированы в виде комментариев в коде.
    - При изменении поведения — обновлять документацию.
    - Для геттеров и сеттеров документация не обязательна, если их поведение очевидно.

Эти правила JSDoc обеспечивают полную и понятную документацию кода, которая может быть использована для генерации внешней документации.

## 4. Архитектурные принципы

На основе анализа кодовой базы были выявлены следующие архитектурные принципы и паттерны проектирования:

1. **Модульная архитектура** с разделением кода по функциональным директориям:
   - `controller/` - компоненты управления (TranslateController)
   - `models/` - основные модели и сущности системы (Dot, System, Drawer, Tracker, Vector)
   - `utils/` - утилитарные функции и вспомогательные инструменты (math, throttle)

2. **Принцип единственной ответственности (SRP)** реализован в каждом классе:
   - `Dot` - отвечает за поведение физического тела
   - `System` - управляет коллекцией тел
   - `Drawer` - отвечает за отрисовку элементов
   - `TranslateController` - управляет трансформацией (масштаб и смещение)
   - `Tracker` - отслеживает выбранное тело

3. **Паттерн Singleton** используется в `TranslateController` для обеспечения единственного экземпляра контроллера трансформации:
   - Реализован через статическое свойство `_instance`
   - Конструктор возвращает существующий экземпляр при повторном вызове

4. **Инверсия зависимостей** реализована через внедрение зависимостей в конструкторы:
   - `Drawer` получает контекст Canvas через конструктор или метод `setContext`
   - `TranslateController` получает контекст Canvas через параметры конструктора

5. **Принципы SOLID** в целом соблюдаются:
   - SRP: каждый класс имеет одну ответственность
   - OCP: классы открыты для расширения через наследование (например, интерфейсы)
   - LSP: наследование интерфейсов соблюдается (классы реализуют интерфейсы)
   - ISP: интерфейсы специфичны и не содержат лишних методов
   - DIP: зависимости передаются извне

6. **Использование интерфейсов** для определения контрактов:
   - `IDot`, `IDotStartProps`, `ICoords` - интерфейсы для сущностей
   - `ISystem`, `ITranslateController` - интерфейсы для классов

7. **Разделение ответственностей** между компонентами:
   - Модели (`Dot`, `System`) отвечают за логику симуляции
   - Вью (`Drawer`) отвечает за отрисовку
   - Контроллеры (`TranslateController`) отвечают за управление пользовательским интерфейсом

8. **Файловая структура** отражает архитектуру приложения:
   - Каждый класс находится в отдельном файле
   - Имена файлов соответствуют именам классов в lowercase
   - Связанные по функционалу классы группируются в директориях

9. **Минимизация связности** между модулями:
   - Импорты организованы явно
   - Зависимости только от необходимых модулей
   - Отсутствует циклическая зависимость между модулями

10. **Расширяемость** системы обеспечивается:
    - Через использование интерфейсов
    - Через модульную архитектуру
    - Через соблюдение принципа открытости/закрытости

Эти архитектурные принципы обеспечивают масштабируемость, тестируемость и поддерживаемость кодовой базы.

## 5. Обработка ошибок

На основе анализа кодовой базы были выявлены следующие подходы к обработке ошибок:

1. **Проверка существования элементов** перед использованием:
   - В `index.ts` проверяется наличие canvas элемента перед использованием
   - В `handlers.ts` проверяется наличие canvas и его контекста перед доступом к ним

2. **Использование throw для фатальных ошибок**:
   - В `index.ts` используется `throw new Error()` при невозможности получить 2D контекст Canvas

3. **Использование console.error для неперехватываемых ошибок**:
   - В `translateController.ts` при отсутствии props выводится сообщение об ошибке через `console.error`
   - В `handlers.ts` при отсутствии canvas выводится сообщение об ошибке через `console.error`

4. **Отсутствие try-catch блоков**:
   - В проекте не используются try-catch блоки для перехвата исключений
   - Обработка ошибок осуществляется через проверку условий и возврат null/undefined

5. **Возврат null/undefined при ошибке**:
   - В `handlers.ts` функция `getCanvasClickCoors` возвращает undefined при ошибках
   - В `draw.ts` методы возвращают void при отсутствии контекста

6. **Проверка входных параметров**:
   - В `draw.ts` методы проверяют наличие контекста перед использованием
   - В `translateController.ts` проверяются входные параметры для анимации

7. **Отсутствие централизованной системы обработки ошибок**:
   - Каждый модуль обрабатывает ошибки самостоятельно
   - Нет общего обработчика ошибок для всего приложения

8. **Использование опциональных цепочек вызовов**:
   - В `handlers.ts` используется опциональная цепочка вызовов (`canvas?.getContext`) для безопасного доступа к вложенным свойствам

Обработка ошибок в проекте в основном основана на профилактических проверках и возврате значений по умолчанию, а не на перехвате исключений. Это соответствует стилю программирования в TypeScript с активным использованием проверок типов и условий.

**Рекомендации по улучшению обработки ошибок:**

1. Ввести централизованную систему обработки ошибок через создание сервиса `ErrorService`
2. Добавить try-catch блоки для критических асинхронных операций
3. Реализовать систему логирования ошибок с возможностью отправки в monitoring-сервис
4. Добавить валидацию входных параметров в публичные методы классов
5. Создать пользовательские типы ошибок для разных категорий ошибок (NetworkError, ValidationError и т.д.)
6. Реализовать обработку ошибок на уровне UI для отображения пользователю
7. Добавить обработку ошибок при работе с таймерами и анимациями
8. Ввести стандартные практики обработки ошибок для всех компонентов приложения

Текущий подход обеспечивает базовую защиту от ошибок, но для production-приложения рекомендуется более полная и централизованная система обработки ошибок.

## 6. Типизация

На основе анализа кодовой базы были выявлены следующие правила типизации:

1. **Использование TypeScript** для полной типизации кодовой базы:
   - Все файлы имеют расширение `.ts`
   - Все переменные, параметры и возвращаемые значения имеют явные ��ипы

2. **Интерфейсы для определения структур данных**:
   - Используются префиксы `I` для именования интерфейсов (`IDot`, `ICoords`, `IVector`)
   - Интерфейсы определяют контракты для объектов и классов
   - Опциональные свойства обозначаются знаком `?`

3. **Аннотации типов для параметров и возвращаемых значений**:
   - Все параметры функций и методов имеют типы
   - Все возвращаемые значения имеют типы
   - Используются сложные типы, включая объединения (`|`) и массивы (`[]`)

4. **Типизация коллекций**:
   - Массивы типизируются явно: `IDot[]`, `ICoords[]`
   - Используются дженерики в утилитах: `throttle<A>`

5. **Опциональные цепочки вызовов**:
   - Используется оператор `?.` для безопасного доступа к свойствам
   - Используется оператор `??` для предоставления значений по умолчанию

6. **Типизация событий**:
   - Параметры обработчиков событий имеют типы: `MouseEvent`, `KeyboardEvent`

7. **Импорты типов**:
   - Используется `import type` для импорта только типов, которые не должны попадать в рантайм
   - Пример: `import type { ICoords, IDot } from "./dot";`

8. **Литеральные типы**:
   - Используются литеральные типы для ключевых значений
   - Пример: `case 81:`, `case 87:` - числовые литералы для кодов клавиш

9. **Объединенные типы**:
   - Используются для представления значений с несколькими возможными типами
   - Пример: `IDot | null` для опциональных ссылок на объекты

10. **Типизация конструкторов**:
    - Параметры конструкторов имеют типы
    - Значения по умолчанию имеют соответствующие типы

**Рекомендации по улучшению типизации:**

1. Ввести кастомные типы для часто используемых комбинаций вместо литеральных типов
2. Создать типы для параметров конфигурации вместо использования анонимных объектов
3. Добавить типы для всех функций верхнего уровня
4. Использовать `const assertions` для литеральных объектов, которые не должны изменяться
5. Ввести типы для событий пользовательского интерфейса
6. Создать типы для параметров анимации и трансформации
7. Добавить типы для всех опциональных параметров конструкторов
8. Использовать `enum` для группировки связанных литеральных типов (например, коды клавиш)

Система типизации в проекте хорошо продумана и обеспечивает высокий уровень безопасности типов, что снижает количество ошибок времени выполнения.

## 7. Производительность

На основе анализа кодовой базы были выявлены следующие подходы к обеспечению производительности:

1. **Использование requestAnimationFrame для анимаций**:
   - В `index.ts` используется `requestAnimationFrame` для рендеринга кадров
   - В `tracker.ts` используется `requestAnimationFrame` для анимации отслеживания тела

2. **Использование setInterval для регулярных обновлений**:
   - В `index.ts` используется `setInterval` с интервалом 30мс для обновления физики симуляции

3. **Оптимизация обработки событий мыши**:
   - В `translateController.ts` используется утилита `throttle` для ограничения частоты обработки событий движения мыши
   - Интервал троттлинга установлен в 20мс

4. **Оптимизация обработки колесика мыши**:
   - В `translateController.ts` используется утилита `throttle` для обработки события `wheel`
   - Интервал троттлинга установлен в 20мс

5. **Анимации с использованием setInterval**:
   - Для анимации масштабирования и перемещения используются `setInterval` с интервалом 20мс
   - Анимации завершаются с помощью `clearInterval`

6. **Оптимизация математических операций**:
   - В `math.ts` используется `toFixed` и `Number` для округления чисел
   - Результаты округляются до 4 знаков после запятой по умолчанию

7. **Ограничение длины истории координат**:
   - В `draw.ts` ограничено количество сохраняемых координат орбиты (до 500 точек)
   - При превышении лимита удаляются старые координаты с помощью `shift()`


8. **Оптимизация отрисовки**:
   - Перед отрисовкой каждого кадра выполняется `clearRect` для очистки холста
   - Используется `setTransform` для сброса трансформации перед отрисовкой

**Рекомендации по улучшению производительности:**

1. Заменить `setInterval` на `requestAnimationFrame` для обновления физики симуляции, чтобы синхронизировать обновления с частотой обновления экрана
2. Оптимизировать алгоритм вычисления гравитационных сил в `computeGravityForcesVector`, так как он имеет сложность O(n²)
3. Реализовать пространственное разбиение (например, quadtree) для уменьшения количества вычислений гравитации между удаленными телами
4. Добавить frustum culling для отрисовки только видимых тел
5. Оптимизировать хранение истории координат, используя ring buffer вместо массива с `shift()`
6. Ввести уровни детализации (LOD) для отрисовки тел в зависимости от расстояния до камеры
7. Кэшировать вычисления, которые не изменяются между кадрами
8. Оптимизировать обработку событий, используя делегирование событий на уровне документа
9. Минимизировать рефлоу и репейнт при изменениях стилей

Производительность в проекте обеспечивается через использование стандартных методов оптимизации анимаций и обработки событий, но есть возможности для значительного улучшения, особенно в вычислительно интенсивных частях симуляции.

## 8. Тестируемость

Поскольку в проекте отсутствуют тесты, составлю правила, которым необходимо следовать при их написании:

1. **Организация тестов**:
   - Создать директорию `tests/` в корне проекта
   - Размещать тесты по структуре, соответствующей src/: `tests/unit/`, `tests/integration/`
   - Для каждого файла в src/ создавать соответствующий тестовый файл с суффиксом `.test.ts`

2. **Выбор тестового фреймворка**:
   - Использовать Jest как основной фреймворк для тестирования
   - Jest хорошо поддерживает TypeScript и предоставляет встроенные моки и спайы

3. **Настройка тестовой среды**:
   - Добавить конфигурацию Jest в package.json или отдельный файл `jest.config.js`
   - Настроить транспиляцию TypeScript через `ts-jest`
   - Настроить мокирование для DOM элементов и Canvas API

4. **Тестирование юнитов**:
   - Писать юнит-тесты для всех классов и функций
   - Тестировать каждый метод класса с различными сценариями
   - Покрывать как позитивные, так и негативные сценарии
   - Для класса Dot тестировать методы move(), accelerate(), computeGravityForce()
   - Для класса Vector тестировать методы addVector(), toDecartCoords(), toPolarCoords()


5. **Тестирование взаимодействий**:
   - Писать интеграционные тесты для взаимодействия между компонентами
   - Тестировать взаимодействие System с Dot
   - Тестировать взаимодействие Drawer с Canvas контекстом
   - Тестировать взаимодействие TranslateController с событиями

6. **Мокирование зависимостей**:
   - Мокировать CanvasRenderingContext2D в тестах
   - Мокировать DOM элементы и события
   - Использовать моки для таймеров (setTimeout, setInterval)


7. **Тестирование асинхронного кода**:
   - Использовать async/await для тестирования асинхронных операций
   - Тестировать методы, использующие requestAnimationFrame
   - Проверять корректность работы с промисами и коллбэками

8. **Покрытие кода**:
   - Настроить инструменты для измерения покрытия кода (istanbul)
   - Стремиться к покрытию не менее 80% для ключевых модулей
   - Фокусироваться на покрытии бизнес-логики

9. **Написание читаемых тестов**:
   - Использовать describe/it блоки для структурирования тестов
   - Писать понятные названия тестов, описывающие поведение
   - Использовать Given-When-Then или Arrange-Act-Assert паттерн

10. **Тестирование производительности**:
    - Добавить бенчмарки для вычислительно интенсивных методов
    - Тестировать производительность computeGravityForcesVector при большом количестве тел
    - Мониторить регрессию производительности

11. **CI/CD интеграция**:
    - Настроить запуск тестов в GitHub Actions
    - Добавить проверку покрытия кода
    - Запускать тесты при каждом коммите и pull request

12. **Документирование тестов**:
    - Писать комментарии для сложных тестовых сценариев
    - Поддерживать актуальность тестов при изменении кода
    - Документировать сложные моки и заглушки

Эти правила обеспечат создание надежной и поддерживаемой тестовой базы для проекта, что повысит качество кода и упростит дальнейшую разработку.

## 9. Пользовательская документация

Для обеспечения удобства использования и поддержки проекта необходимо создавать понятную пользовательскую документацию. Она предназначена для конечных пользователей, разработчиков интеграций и технических писателей.

1. **Типы пользовательской документации**:
   - **Руководство пользователя** — как пользоваться симулятором: управление камерой, добавление планет, пауза и т.д.
   - **Руководство разработчика** — как подключить, настроить и расширить симулятор.
   - **API Reference** — автоматически генерируемая документация на основе JSDoc (если используется).
   - **Примеры использования** — готовые примеры кода для типичных задач (например, инициализация, добавление тел, настройка физики).

2. **Формат и хранение**:
   - Документация хранится в директории `docs/` в корне проекта.
   - Основной формат — Markdown (`.md`).
   - Можно использовать статические генераторы (например, Docusaurus, MkDocs) для публикации.

3. **Содержание руководства пользователя**:
   - Краткое описание симулятора.
   - Управление: клавиши, мышь (масштаб, перемещение).
   - Добавление и удаление тел.
   - Настройка физических параметров.
   - Режимы отображения (орбиты, векторы и т.д.).
   - Экспорт/импорт конфигураций.

4. **Содержание руководства разработчика**:
   - Установка и запуск.
   - Структура проекта.
   - Подключение к сторонним приложениям.
   - Настройка параметров инициализации.
   - Расширение функциональности (плагины, кастомные классы).

5. **Примеры кода**:
   - Все примеры должны быть протестированы и рабочими.
   - Примеры размещаются в `docs/examples/`.
   - Каждый пример — отдельный `.md` или `.ts` файл с пояснениями.

6. **Обновление документации**:
   - Документация обновляется при каждом значительном изменении функциональности.
   - Обязательно указывать версию симулятора в заголовке.

7. **Стандарты качества**:
   - Ясный и понятный язык.
   - Избегать жаргона, если не требуется.
   - Использовать скриншоты и диаграммы при необходимости.
   - Проверять орфографию и грамматику.

Эти правила помогут создать полную, понятную и поддерживаемую пользовательскую документацию, которая будет полезна как разработчикам, так и пользователям симулятора.

## 10. Правила оформления коммитов

Все коммиты должны быть на русском языке и понятно описывать внесённые изменения.

### Формат коммита

Коммит должен начинаться с глагола в повелительном наклонении, кратко описывающего суть изменений. Допускается указание компонента или модуля в начале (в скобках).

**Примеры корректных коммитов:**
- Добавлен рендер орбит планет
- (Физика) Обновлена модель гравитации
- Исправлена ошибка масштабирования камеры
- Добавлено управление скоростью симуляции

**Что не допускается:**
- Использование английских слов и фраз
- Общие формулировки вроде "исправления", "обновление"
- Описание, не отражающее сути изменений

Старайтесь делать небольшие, логически завершённые коммиты.
