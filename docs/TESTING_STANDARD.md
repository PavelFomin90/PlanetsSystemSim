# Стандарт тестирования

## 1. Организация тестов

1. **Структура каталогов**:
   - Создать директорию `tests/` в корне проекта
   - Размещать тесты по структуре, соответствующей src/: `tests/unit/`, `tests/integration/`, `tests/e2e/`
   - Для каждого файла в src/ создавать соответствующий тестовый файл с суффиксом `.test.ts` в аналогичной структуре каталогов

2. **Именование тестовых файлов**:
   - Тестовые файлы должны иметь суффикс `.test.ts` или `.spec.ts`
   - Имя тестового файла должно соответствовать имени тестируемого файла
   - Пример: для `user.ts` создать `user.test.ts`

3. **Группировка тестов**:
   - Использовать `describe` блоки для группировки тестов по функциональности
   - Вложенные `describe` блоки для группировки по методам или сценариям
   - Использовать `beforeEach`, `afterEach`, `beforeAll`, `afterAll` для настройки и очистки тестового окружения

## 2. Выбор тестового фреймворка

1. **Основной фреймворк**:
   - Использовать Jest как основной фреймворк для тестирования
   - Jest хорошо поддерживает TypeScript, имеет встроенные моки, спайы и тайм-ауты
   - Альтернативы: Mocha, Jasmine, Vitest

2. **Инструменты для end-to-end тестирования**:
   - Для тестирования пользовательского интерфейса использовать Cypress или Playwright
   - Эти инструменты позволяют тестировать приложение в реальном браузере

3. **Тестирование производительности**:
   - Использовать специализированные инструменты для бенчмарков и измерения производительности
   - Пример: benchmark.js для микробенчмарков

## 3. Настройка тестовой среды

1. **Конфигурация Jest**:
   - Добавить конфигурацию Jest в package.json или отдельный файл `jest.config.js`
   - Настроить транспиляцию TypeScript через `ts-jest`
   - Настроить мокирование для внешних зависимостей и API

2. **Настройка пре-процессоров**:
   - Настроить обработку различных типов файлов (CSS, изображения и т.д.)
   - Использовать заглушки для файлов, которые не могут быть выполнены в Node.js окружении

3. **Настройка покрытия кода**:
   - Настроить инструменты для измерения покрытия кода (istanbul)
   - Установить минимальный порог покрытия для CI/CD
   - Настроить отчеты о покрытии в различных форматах (HTML, JSON, текст)

4. **Настройка среды выполнения**:
   - Настроить разные среды выполнения тестов (development, production, test)
   - Настроить мокирование глобальных объектов (window, document, localStorage)

## 4. Тестирование юнитов

1. **Цель юнит-тестирования**:
   - Проверка корректности работы отдельных функций и методов
   - Проверка поведения классов в изоляции
   - Проверка граничных условий и обработки ошибок

2. **Покрытие тестами**:
   - Писать юнит-тесты для всех публичных методов и функций
   - Покрывать как позитивные, так и негативные сценарии
   - Проверять обработку граничных условий (null, undefined, крайние значения)

3. **Принципы написания тестов**:
   - Каждый тест должен проверять только одну вещь
   - Тесты должны быть независимыми друг от друга
   - Тесты должны быть воспроизводимыми и детерминированными

4. **Структура теста (AAA - Arrange, Act, Assert)**:
   - **Arrange**: настройка тестового окружения, создание моков, подготовка данных
   - **Act**: выполнение тестируемого действия
   - **Assert**: проверка ож��даемых результатов

5. **Название тестов**:
   - Использовать понятные названия, описывающие поведение
   - Название должно отвечать на вопрос "Что тестируется и при каких условиях?"
   - Пример: "должен корректно вычислять сумму двух чисел"

## 5. Тестирование взаимодействий

1. **Цель интеграционного тестирования**:
   - Проверка корректности взаимодействия между компонентами
   - Проверка работы модулей в составе системы
   - Проверка интеграции с внешними системами (API, базы данных)

2. **Типы интеграционных тестов**:
   - Тестирование взаимодействия между классами и модулями
   - Тестирование работы с базой данных (CRUD операции)
   - Тестирование HTTP API (запросы, ответы, статус-коды)
   - Тестирование событийной архитектуры

3. **Принципы написания интеграционных тестов**:
   - Тесты должны использовать реальные зависимости, когда это возможно
   - Для внешних систем использовать моки или тестовые окружения
   - Тесты должны быть изолированы от внешних факторов

## 6. Мокирование зависимостей

1. **Цель мокирования**:
   - Изоляция тестируемого кода от внешних зависимостей
   - Ускорение выполнения тестов
   - Проверка различных сценариев (успех, ошибка, тайм-аут)

2. **Типы моков**:
   - **Моки**: объекты, которые проверяют, был ли вызван метод с правильными параметрами
   - **Спайы**: моки, которые также вызывают реальный метод
   - **Заглушки (Stubs)**: объекты, которые возвращают предопределенные значения
   - **Фейки (Fakes)**: упрощенные реализации реальных зависимостей

3. **Что мокировать**:
   - Внешние API и HTTP запросы
   - Базы данных и файловую систему
   - Глобальные объекты (window, document)
   - Таймеры (setTimeout, setInterval)
   - Canvas API и другие браузерные API

4. **Инструменты для мокирования**:
   - Использовать встроенные моки Jest
   - Для сложных сценариев использовать специализированные библиотеки
   - Создавать пользовательские моки для сложных зависимостей

## 7. Тестирование асинхронного кода

1. **Подходы к тестированию асинхронного кода**:
   - Использовать async/await для тестирования асинхронных операций
   - Использовать done() callback для ручного управления завершением теста
   - Использовать встроенные механизмы Jest для работы с промисами

2. **Тестирование различных сценариев**:
   - Позитивные сценарии (успешное выполнение)
   - Негативные сценарии (ошибки, исключения)
   - Тайм-ауты и отмена операций

3. **Тестирование колбэков**:
   - Проверка вызова колбэков с правильными параметрами
   - Проверка порядка вызова колбэков
   - Проверка обработки ошибок в колбэках

4. **Тестирование промисов**:
   - Проверка разрешения промиса с ожидаемым значением
   - Проверка отклонения промиса с ожидаемой ошибкой
   - Проверка цепочек промисов

5. **Тестирование async/await**:
   - Использование async/await в тестах для упрощения чтения кода
   - Проверка обработки исключений с помощью try/catch

## 8. Покрытие кода

1. **Цель измерения покрытия**:
   - Оценка полноты тестового покрытия
   - Выявление не протестированных участков кода
   - Мониторинг прогресса в улучшении тестового покрытия

2. **Типы покрытия**:
   - **Покрытие строк (Line coverage)**: какой процент строк кода был выполнен
   - **Покрытие функций (Function coverage)**: какой процент функций был вызван
   - **Покрытие ветвлений (Branch coverage)**: какой процент ветвлений (if/else) был выполнен
   - **Покрытие операторов (Statement coverage)**: какой процент операторов был выполнен

3. **Целевые показатели**:
   - Стремиться к покрытию не менее 80% для ключевых модулей
   - Фокусироваться на покрытии бизнес-логики
   - Не гнаться за 100% покрытием в ущерб качеству тестов

4. **Настройка в CI/CD**:
   - Настроить проверку минимального порога покрытия
   - Запрещать мерж в основную ветку при падении покрытия ниже порога
   - Генерировать отчеты о покрытии для анализа

## 9. Написание читаемых тестов

1. **Использование describe/it блоков**:
   - Использовать describe для группировки связанных тестов
   - Использовать it (или test) для описания конкретного теста
   - Вложенная структура describe блоков для сложных сценариев

2. **Паттерны именования тестов**:
   - Использовать Given-When-Then паттерн
   - Использовать Arrange-Act-Assert паттерн
   - Использовать BDD (Behavior-Driven Development) стилистику

3. **Комментарии и документирование**:
   - Писать комментарии для сложных тестовых сценариев
   - Документировать сложные моки и заглушки
   - Поддерживать актуальность тестов при изменении кода

4. **Принципы чистого кода в тестах**:
   - Избегать дублирования кода с использованием beforeEach и хелперов
   - Поддерживать тесты аккуратными и понятными
   - Рефакторить тесты так же, как и production код

## 10. Тестирование производительности

1. **Цель тестирования производительности**:
   - Выявление узких мест в производительности
   - Мониторинг регрессии производительности
   - Обеспечение стабильной работы приложения под нагрузкой

2. **Типы тестов производительности**:
   - **Микробенчмарки**: измерение производительности отдельных методов
   - **Макробенчмарки**: измерение производительности целых сценариев
   - **Тесты нагрузки**: проверка работы приложения под высокой нагрузкой
   - **Тесты стресса**: проверка поведения при экстремальной нагрузке

3. **Измерение производительности**:
   - Измерение времени выполнения критических методов
   - Измерение использования памяти
   - Измерение количества DOM операций
   - Измерение FPS для анимаций

4. **Установка базовых показателей**:
   - Создание бейзлайнов для ключевых операций
   - Мониторинг отклонений от бейзлайнов
   - Настройка оповещений при превышении порогов

## 11. CI/CD интеграция

1. **Настройка запуска тестов**:
   - Настроить запуск тестов в CI/CD системе (GitHub Actions, GitLab CI и т.д.)
   - Запускать тесты при каждом коммите и pull request
   - Запускать разные типы тестов (unit, integration, e2e) на разных этапах

2. **Проверка покрытия кода**:
   - Интеграция с инструментами анализа покрытия (CodeCov, Coveralls)
   - Проверка минимального порога покрытия
   - Блокировка мержа при падении покрытия

3. **Отчеты и уведомления**:
   - Генерация отчетов о результатах тестирования
   - Отправка уведомлений о падающих тестах
   - Интеграция с системами мониторинга и трекинга ошибок

4. **Оптимизация времени выполнения**:
   - Параллельный запуск тестов
   - Кэширование зависимостей
   - Запуск только измененных тестов при локальной разработке

## 12. Поддержка тестовой базы

1. **Обновление тестов**:
   - Поддерживать актуальность тестов при изменении кода
   - Обновлять тесты при рефакторинге
   - Удалять устаревшие тесты

2. **Борьба с хрупкими тестами**:
   - Избегать тестов, зависящих от внешних факторов
   - Минимизировать количество моков, когда это возможно
   - Использовать более стабильные селекторы в e2e тестах

3. **Документирование тестовой стратегии**:
   - Поддерживать актуальную документацию по тестированию
   - Описывать типы тестов и их назначение
   - Описывать инструменты и подходы

4. **Обучение и передача знаний**:
   - Обучать новую команду подходам к тестированию
   - Проводить код-ревью тестов
   - Совместно разрабатывать сложные тестовые сценарии
